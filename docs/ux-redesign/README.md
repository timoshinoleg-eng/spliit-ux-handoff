# Spleet Mini App — UX-редизайн (ветка `muse/spleet-ux-redesign`)

Демо: `npm ci && npm run build`, затем `python -m http.server 8000 --bind 127.0.0.1 --directory dist`
и http://127.0.0.1:8000/ → «Посмотреть демоверсию без Telegram».
Скриншоты: `before/` — исходное состояние, `after/` — после редизайна,
имена файлов совпадают сценарий в сценарий.

## Что изменилось

1. **Первый экран группы — два режима (A/B), переключатель в демо.**
   Под сводкой баланса — сегмент «Первый экран: История / Расчёты»
   (только в демо, выбор сохраняется в `localStorage`).
   - **A «История» (по умолчанию, рекомендуется):** группа открывается на
     вкладке «Расходы», баланс виден сверху. Контекст (за что платили)
     всегда перед глазами, расчёты — в один тап на «Долги».
   - **B «Расчёты»:** группа открывается сразу на «Долги» — «Кому и сколько
     вернуть» и кнопки «Отметить возврат» / «Напомнить о долге».
2. **Долги различаются текстом И знаком суммы** (раньше — только цветом
   и словами): «Вы должны −1 800,00 ₽», «Вам должны +1 800,00 ₽».
   Долги между другими участниками — без знака (это не ваши деньги),
   направление словами: «Иван → Анна». Нулевой баланс — нейтральный
   «Долгов нет · 0,00 ₽», а не зелёный.
3. **Состояния с явным следующим действием:**
   - Пустая группа: «Расходов пока нет…» + кнопка «Добавить первую трату».
   - Просроченное приглашение: «Приглашение не найдено…» + «Создать свою
     группу» и «Обновить список».
   - Отказ сохранения: ошибка теперь видна внутри формы
     (`role="alert"`, поля сохранены) — раньше только исчезающий тост.
   - Неопределённый результат возврата: панель «Проверьте запись возврата»
     с «Проверить запись» / «Отменить незавершённую запись» (логика
     `settlement-recovery.js` не менялась).
   - Загрузка: под «Загрузка…» добавлена подсказка, что делать, если
     она затянулась.
4. **Тёмная тема в демо:** кнопка ☾/☀ в шапке (только в демо; в Telegram
   тема берётся из клиента). Выбор сохраняется.
5. **320–430 px:** на ≤360 px кнопки действий группы — в столбик,
   шрифт метрик меньше, карточки долгов — в одну колонку; переполнений нет.
6. **Клавиатура:** порядок Tab — тема → назад → переключатель входа →
   действия → вкладки → строки → нижняя навигация; `:focus-visible`
   (сплошной контур 2 px цвета бренда) на всех интерактивных элементах.

## Сравнение вариантов входа (A / B / прод)

| | A — история с балансом | B — расчёты первым экраном | Прод — список групп |
|---|---|---|---|
| Первый экран | История трат, баланс сверху | «Кому и сколько вернуть» | Список «Ваши группы» |
| Сильная сторона | Контекст: видно, за что деньги; баланс всегда рядом | Ближайшее действие — закрыть долг | Масштаб: выбор между группами |
| Слабая сторона | Долги — в один тап дальше | Не видно, откуда взялся долг | Внутри группы нужен ещё один шаг |
| Кому подходит | Постоянные пользователи, активная группа | Момент «пора рассчитаться» | Пользователи с несколькими группами |

**Рекомендация: A по умолчанию.** Это не спор с продом, а уровни:
список групп остаётся входом на уровне приложения (как в проде),
а внутри группы первым экраном становится история с видимым балансом —
потому что в активной группе чаще смотрят «что нового и сколько я должен»,
чем «кому перевести прямо сейчас». B остаётся переключателем в один тап —
для момента расчёта. Решение проверяемо: в демо оба режима снимаются
одинаковыми сценариями (см. `18-entry-b-390-light`).

## Сравнение с продом (проверено в браузере, только просмотр)

- Прод: первый экран — список групп, только светлая тема, переключателя
  тёмной темы нет. Внутригрупповые экраны без группы и входа в Telegram
  недоступны — поэтому «до»-скриншоты из локального демо остаются
  главным материалом сравнения.
- Наблюдения (зафиксированы, не чиню — это прод, не эта ветка):
  кнопка «Расходы» в нижней навигации не открывает экран без группы;
  при загрузке вне Telegram на несколько секунд появляется тост
  «WebAppServerlessInitDataUnavailable»; стрелка «‹» на экране создания
  группы с первого нажатия не вернула на главную; бренд приложения
  «Spliit / spliit.», а бот — @spleetofficial_bot.

Источник задач — разбор второго мнения (аудит, §1–5). Его готовый код
(раздел 6) НЕ копировался: все правки написаны заново, точечно,
поверх текущего кода ветки. Денежная логика по-прежнему неприкосновенна:
сам алгоритм `splitExpense` не менялся.

1. **Демо-движок — на тот же Hamilton.** `demoView()` в `web/app.js`
   считал доли через `Math.floor` + остаток последнему участнику, а форма
   уже использовала `splitExpense`. Теперь демо считает тем же
   `splitExpense` (он уже был импортирован). Проверка: трата 10,01 ₽
   на троих даёт набор {3,34; 3,34; 3,33} и никогда 3,35
   (см. `29-hamilton-1001-390-light`; node-проверка `splitExpense`

   «На 3 чел. · Ваша доля: 1 800,00 ₽» — доля считается тем же
   `splitExpense` для этой траты; плательщик уже стоит в первой строке,

   вместо доли — «Возврат долга». Если долю посчитать нельзя

   просто не показывается, рендер не падает.

## Третий заход — точный статус сохранения, «Назад» в окне возврата, без запасного округления

### 1. Точный статус сохранения (вместо «Не сохранено» при неизвестном исходе)

Три случая различаются явно:

- **Явный отказ** — ошибка валидации или отклонение сервером с
  причиной. Панель в форме: «Трата «{название}» не сохранена.» +
  причина + «Исправьте данные и отправьте ещё раз — введённое не
  пропало.» Введённые поля сохраняются; дополнительно висит
  постоянный тост ошибки (как во втором заходе).
- **Потерянный ответ** — сеть оборвалась, запрос мог уйти. Панель
  в форме с точным заголовком **«Не удалось проверить, сохранилась
  ли трата»** + «Сеть оборвалась, когда мы отправляли трату
  «{название}» ({сумма}). Возможно, она уже сохранена — сначала
  проверьте, а потом отправляйте ещё раз.» Кнопка **«Проверить,
  сохранилась ли трата»** — повторный запрос группы и поиск траты
  по её ID: найдена → переход в группу, тост «Трата сохранена»;
  не найдена → «Траты «{название}» в группе нет…» (можно отправить
  ещё раз тем же номером); проверка недоступна → «Проверить не
  удалось — сеть недоступна…». Поля и исходный ID траты
  сохраняются: `S.newExpenseId` генерируется один раз при открытии
  формы и после неудачной отправки не перегенерируется, форма не
  сбрасывается. Подсказка о повторе привязана к операции:
  «Повторная отправка идёт с тем же номером траты: второй строки
  не появится, но запись может обновиться.»
- **Запись подтверждена, список не обновился** — сохранение прошло,
  а повторная загрузка группы упала. Форма закрывается, на домашнем
  экране зелёный баннер **«Трата сохранена»** («Трата «{название}»
  сохранена, но список группы не обновился.») с кнопками **«Открыть
  группу»** (повторная загрузка; при неудаче баннер остаётся) и
  «Скрыть». Плюс тост «Трата сохранена».

**Честная оговорка.** Стабильный ID траты не даёт второй строки
расхода, но повторная отправка может обновить запись и добавить
событие в историю — «точно-один-раз» шире этого контракта не
заявляется. Создание группы и вступление — отдельные контракты, их
не трогали.

**Демо-хуки отказа (только демо, только для проверок).**
`?demoFail=lostExpense` — адаптер сначала записывает расход,
затем возвращает сетевую ошибку (ровно сценарий «запрос мог
уйти»); срабатывает один раз. `?demoFail=refreshFail` — после
следующего успешного сохранения ломает ровно одну перезагрузку
группы (не первую встречную `group_get`). Вне демо хуки
недоступны: флаг читается из `location.search` демо-адаптера.

### 2. Telegram «Назад» в окне возврата

Стек «назад» для модалок (`modalBackStack` в `web/app.js`): при
открытии окна возврата регистрируется обработчик закрытия;
`tg.BackButton` сначала спрашивает стек, потом роутер
(`web/native-ux.js`: `if(closeTopModal?.())return;`).
Первое нажатие закрывает окно, оставляет пользователя на вкладке
«Долги» и **возвращает фокус на кнопку, открывшую окно**
(элемент запоминается при открытии; если его успел уничтожить
перерендер — ищется замена по получателю). Следующее нажатие —
обычная навигация. Открытие окна больше не перерисовывает
страницу под ним (иначе перерендер уничтожал бы кнопку-открыватель
до возврата фокуса).

Основная кнопка окна переименована в **«Записать возврат»**
(было «Подтвердить возврат»); рядом — пояснение, что перевод

### 1. Проверка правки — по содержимому, а не по ID

искала запись по ID. При редактировании этот ID уже существует: если
правка не дошла, проверка находила старую версию, закрывала форму и
ложно показывала «Трата сохранена». Исправление:
`expenseMatchesPayload` сравнивает сохранённую запись с отправленной
правкой — название, сумму в копейках, плательщика, `splitMode` и доли по
участникам (без учёта порядка). Найдена старая версия или результат
нельзя подтвердить однозначно — новый статус «прежняя версия», форма и
введённые данные остаются. Успех — только после подтверждения изменений.

(обрыв до записи) и `?demoFail=lostEditAfter` (запись, потом обрыв).

в хранилище старые значения, форма открыта, статус «прежняя версия»;

`{type: 'NETWORK_ERROR', message: 'Связь прервана'}` форма писала

обработчик (`Error` с полями `.type`/`.code`); `isNetworkError`
проверяет их в первую очередь, совпадение по тексту — только fallback.

и `?demoFail=rejected` (явный отказ сервера). Дефект воспроизведён
через настоящий путь `Serverless.call` в симуляции Telegram
(`shots-round5-tg.mjs`, фейковый `Serverless` с внутристраничным
хранилищем): до исправления локализованная ошибка показывала
